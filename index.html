Case study

Data migration · validation

Explaining about 211K migration mismatches by matching them to error logs

The problem

After a production migration run, a comparison of the legacy source against the migrated data flagged about 211K records where a card and a digital ID disagreed. A flat list that size can't be worked. Nobody knew which differences were migration bugs, which came from bad source data, and which needed a fix at all.

Approach

  • Grouped the mismatches by the combination of card, email and email ID that differed, so identical patterns were counted together.
  • Matched each group against the migration's own pre-processing error logs. If the same IDs had already been logged as errors, the cause was known.
  • Checked the gaps: for each group, reconciled the difference in counts and sampled records by hand to confirm the explanation held.
  • Proposed fixes for each category, such as "fix in the source system" or "the source has to create the missing data", so each had a clear next step.

Each step narrowed the open question until every group had an explanation and a proposed owner of the fix.

Result

Of about 211K mismatched card and digital IDs, 99.98% matched a logged pre-processing error, so almost every difference had a documented cause. Samples traced most of it to bad data in the source system, not to the migration. The open-ended mismatch became a short set of categories, each with a fix proposal, and the final production run of about 1.22 billion records closed at 99.99% accuracy.

What I'd do differently

Match against the error logs earlier. The explanation was sitting in the logs already, and comparing them before the first reconciliation would have cut the manual sampling. recon is a small public version of the grouping idea.
